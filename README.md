# user-service

First microservice extracted from the legacy monolith, following the
**Strangler Fig** pattern. This repository is **independent** from the monolith:
its own dependencies, Dockerfile, configuration, migrations, database and deploy
lifecycle. It does not contain, import or manage the monolith.

At this stage the service is only **created and prepared to receive migrated
data**. Real application traffic is still served by the monolith.

---

## Como executar

```bash
cp .env.example .env
docker compose up --build
```

This starts:

- `user-postgres` — the service's own PostgreSQL (host port `5433`)
- `user-service` — FastAPI app on http://localhost:8000 (runs `alembic upgrade head` on start)

API docs: http://localhost:8000/docs

### Local (without Docker)

```bash
python -m venv .venv && . .venv/Scripts/activate      # Windows
pip install -e ".[dev]"
# start a Postgres and point DATABASE_URL at it (compose exposes one on 5433)
alembic upgrade head
uvicorn app.main:app --reload
```

### Testes

```bash
pip install -e ".[dev]"
docker compose up -d user-postgres        # tests need a real PostgreSQL
pytest
```

  │

No `controller` / `usecase` / `repository` / `gateway` / `factory` layers — this

The User Service **never** connects to the legacy monolith database at runtime.
`DATABASE_URL` must always point at `user-postgres`.

## Endpoints

| Method | Path                      | Status codes            | Description |
|--------|---------------------------|-------------------------|-------------|
| GET    | `/health`                 | 200, 503                | Liveness + DB connectivity check |
| POST   | `/users`                  | 201, 422                | Create a user (id managed by the service) |
| GET    | `/users`                  | 200                     | List users, ordered by id |
| GET    | `/users/{id}`             | 200, 404                | Get one user |
| PUT    | `/users/{id}`             | 200, 404, 422           | Update a user's name |
| DELETE | `/users/{id}`             | 204, 404                | Delete a user |
| POST   | `/internal/users/import`  | 201, 200, 409, 422      | Idempotent import from the legacy monolith |

### Contratos

Error responses share one shape:

```json
{ "error": { "code": "not_found", "message": "User 42 not found", "request_id": "..." } }
```

Every request carries a correlation id: send `X-Request-ID` or one is generated;
it is echoed back on the response and included in every structured (JSON) log line.

`POST /users`
```json
// request
{ "name": "Alice" }
// 201
{ "id": 1, "name": "Alice", "created_at": "2026-09-08T12:00:00Z" }
```

`POST /internal/users/import`
```json
// request
{ "id": 37, "name": "Thiago", "created_at": "2020-01-01T00:00:00Z" }
// 201 -> { "status": "created",   "user": { "id": 37, ... } }
// 200 -> { "status": "unchanged", "user": { "id": 37, ... } }   (same data already present)
// 409 -> { "error": { "code": "import_conflict", "conflicts": { "name": { "existing": "...", "incoming": "..." } } } }
```

## Estrutura do banco

```text
users
  id          BIGINT  PRIMARY KEY  GENERATED BY DEFAULT AS IDENTITY
  name        VARCHAR(255)  NOT NULL
  created_at  TIMESTAMPTZ   NOT NULL  DEFAULT now()
```

Same shape as the monolith's `users` table (`id`, `name`, `created_at`), so
migrated rows map 1:1. `sales` stays in the monolith and is out of scope here.

---

## Decisão de IDs

### Por que preservar os IDs do monólito

In the monolith, `sales.user_id` is a foreign key to `users.id`. Those id values
are referenced by existing sales rows (and potentially other systems, logs,
exports). If the User Service assigned **new** ids to migrated users, every
`sales.user_id` would silently point at the wrong person. Identity must be
preserved across the migration, so an imported user with `id = 37` stays `id = 37`.

### Criação normal vs importação

| | `POST /users` | `POST /internal/users/import` |
|---|---|---|
| Origin | new users created by the new system | rows coming from the legacy monolith |
| `id` | assigned by PostgreSQL identity | supplied explicitly, preserved as-is |
| `created_at` | `now()` | supplied explicitly (optional) |
| Idempotent | no | yes |
| Surface | public | internal, migration-only |

### Importação idempotente

- id absent → insert with the explicit id → `201 { "status": "created" }`
- id present, identical data → no-op → `200 { "status": "unchanged" }`
- id present, **different** data → `409 import_conflict`, nothing is overwritten

So re-running the same import is safe and leaves exactly one row per id.

### Sequence / identity consistency (importante)

The `users.id` column is `GENERATED BY DEFAULT AS IDENTITY`. That lets us insert
explicit ids during import, but the underlying identity **sequence** is not
advanced by those inserts. Without care, after importing ids `1..100` the next
`POST /users` would try to generate `id = 1` and fail with a unique-violation.

After every explicit-id insert, `import_user` calls `resync_identity_sequence()`:

```sql
SELECT setval(
    pg_get_serial_sequence('users', 'id'),
    GREATEST((SELECT COALESCE(MAX(id), 1) FROM users), 1),
    true            -- is_called = true  ->  next value is MAX(id) + 1
);
```

It runs in the same transaction as the insert, is cheap, and is idempotent. Test
`test_normal_create_after_high_id_import` locks this behaviour in: import
`id = 1000`, then `POST /users` returns `id = 1001`.

If a bulk import is done outside this service (e.g. `COPY`), run the same
`setval(...)` statement once afterwards.

## Estado atual da migração

```text
Legacy DB
    users   <--- still the source of truth, used by the monolith
    sales

User DB
    users   <--- new, independent copy (structure ready; filled via import)
```

There is **no automatic synchronization** between the two databases at this
point. No dual-write, no CDC, no messaging. Data lands in the User DB only when
someone calls `POST /internal/users/import`.

## Configuração

All configuration via environment variables (see `.env.example`). No hardcoded
secrets.

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `postgresql+psycopg://user_service:user_service@localhost:5433/user_service` | This service's own PostgreSQL |
| `APP_ENV` | `development` | Environment name (surfaced in `/health`) |
| `LOG_LEVEL` | `INFO` | Root log level |
| `GRACEFUL_SHUTDOWN_SECONDS` | `20` | uvicorn graceful-shutdown window |

## Operação

- **Logs**: structured JSON on stdout, one line per request (`request.start` /
  `request.end`) plus domain events (`user.created`, `user.import.created`, …),
  each tagged with `request_id`.
- **Health**: `GET /health` returns `200` when the DB answers, `503` otherwise.
- **Graceful shutdown**: on `SIGTERM` uvicorn stops accepting connections, drains
  in-flight requests within the shutdown window, then the lifespan hook disposes
  the SQLAlchemy engine (`compose` grants a 30s stop grace period).
